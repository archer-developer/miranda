# Channel-adapter formatting + lit-html chat.js migration

Planning doc, not yet implemented — see "Implementation order" for the
intended sequence when this is picked up.

## Context

Right now Miranda has exactly one place that adapts the reply text per
channel: `appendDownloadFootnotes` (added this session), which only handles
file attachments — everything else (bold/italic/links/lists) is either not
generated by the model at all (the web UI's `inline-text.js` deliberately
only supports backtick code spans, "not a full markdown parser") or would
render as literal asterisks/brackets if it were (Telegram gets no
`parse_mode`, live `ha_assist` speech gets zero stripping).

The user wants two related things:

1. **Channel adapters**: a real, code-enforced separation between the raw
   text stored in history (unchanged, as today) and how each channel
   presents it — Web UI (rich but safe), Telegram (its own HTML subset via
   `parse_mode`), and voice (stripped to natural spoken plain text, no
   links/markup). This generalizes the pattern `Downloads` already
   established this session (structured/derived data, never mixed into
   `Content`) to a second, more general concern: text formatting.
2. **Frontend templating**: the web UI's screens mix `innerHTML` template
   literals with manual `document.createElement` calls; the user wants a
   lightweight, safe templating helper — no React, no build step (this repo
   has none: no `package.json`, no bundler, JS is served as raw ES
   modules). Decided: vendor `lit-html` (templating-only), the same way
   `json-formatter-js` is already vendored as a single committed file.

**Decisions already made with the user** (do not re-litigate):
- Full markdown-lite set: bold, italic, code (exists), links, simple lists.
  Not full CommonMark — no headers/blockquotes/tables/images/nested lists.
- Voice is in scope too (both the live `ha_assist` stream and
  `speak_reply`/`send_telegram`), not just Web/Telegram.
- Vendor lit-html rather than hand-roll a templating helper.
- Migrate exactly one screen this pass — `chat.js` (the largest/most
  tangled at 718 lines) — as the reference pattern; the other 4 screens
  stay as-is for a future pass.

## Workstream A — `internal/replyformat` (new package)

A new, dependency-free package (`internal/replyformat/`) owns the one
canonical parse of a reply's markdown-lite text into a shared AST, plus
three renderers off that same AST. `history.Message.Content` is never
touched by any of this — it stays exactly what the model said, forever, the
same principle `Downloads`/`DownloadRef` established this session.

```go
type BlockType string // "paragraph" | "list"
type Block struct {
    Type     BlockType   `json:"type"`
    Segments []Segment   `json:"segments,omitempty"` // paragraph
    Items    [][]Segment `json:"items,omitempty"`    // list: one run per item
}

type SegmentType string // "text" | "bold" | "italic" | "code" | "link"
type Segment struct {
    Type SegmentType `json:"type"`
    Text string      `json:"text"`
    URL  string      `json:"url,omitempty"` // set only for "link"
}

func Parse(text string) []Block // never errors; malformed markup degrades to literal text
```

**Parsing rules** (`internal/replyformat/replyformat.go`):
- Blocks split on blank lines; within a chunk, consecutive `^[-*] \S` lines
  become one list block, everything else one paragraph block (so one
  blank-line-delimited chunk can still yield paragraph+list, matching how
  the model naturally writes "Вот варианты:\n- Раз\n- Два").
- List-vs-italic disambiguation: `- text`/`* text` (space right after the
  marker) is a list item; `*text*` (no space) is italic — lexically
  distinct, same rule CommonMark uses for the same reason.
- Bold `**text**`, italic `*text*` or `_text_` (underscore variant requires
  a word boundary outside the delimiters, so `snake_case_var` is never
  mis-italicized), code `` `text` `` (highest scan priority, identical
  semantics to the existing JS `CODE_SPAN_RE`), link `[label](url)`.
- No nested emphasis in v1 (segments are a flat enum, not a style bitmask)
  — matches the existing minimal-markdown precedent; additive to extend
  later if it turns out to matter.
- Any unmatched opener degrades to a literal text segment — `Parse` never
  errors and always returns at least one block for non-empty input.

**Renderers**, each a pure function of `[]Block`:
- **Web**: no separate renderer — `Block`/`Segment` already are the wire
  shape (JSON tags above). Computed **on read**, not persisted (it's 100%
  derivable from `Content`; persisting would mean backfilling on every
  future parser-rule tweak). Three attachment points, all outside
  `internal/history`:
  - `InputResponse` (orchestrator.go) gains `Blocks []replyformat.Block`,
    set via `replyformat.Parse(finalText)` where `Reply` is built.
  - `ChatEvent` (orchestrator.go) gains `Blocks []replyformat.Block`,
    computed centrally inside `publishChatMessage` (the one choke point
    every chat-affecting mutation already funnels through) — covers both
    `Handle`'s final-reply publish and the mid-loop tool-call publish.
  - `GET /api/dialogs/{id}` (`webui.go`'s `handleDialogMessages`): wrap in
    a local `messageView{ history.Message; Blocks []replyformat.Block }`
    response type, populated for assistant messages only, right before
    `writeJSON` — keeps `internal/history` itself free of formatting
    concerns, mirroring how `toDownloadRefs` already lives in
    `internal/httpapi`, not `internal/history`.
- **Telegram** (`internal/replyformat/telegram.go`):
  `ToTelegramHTMLChunks(blocks []Block, maxChars int) []string` — escapes
  `&`/`<`/`>` in plain text and inside bold/italic/code/link-label content,
  emits `<b>`/`<i>`/`<code>`/`<a href="...">`, renders list items as `•
  item` lines (Telegram HTML has no `<ul>/<li>`). **Chunking must be
  block-aware**: Telegram's `parse_mode=HTML` hard-rejects the whole
  `sendMessage` call on malformed HTML, so a chunk can never split a tag —
  only fall back to a word-level split within one oversized block, closing
  and reopening any open tag at the forced cut. This is the one genuinely
  tricky correctness requirement in the whole plan; needs its own test with
  a bold/link span straddling a forced chunk boundary.
- **Voice** (`internal/replyformat/voice.go`): `ToVoiceText(blocks []Block)
  string` — bold/italic/code delimiters dropped (bare text kept); a link's
  URL is dropped entirely, only its label text kept; list items and
  paragraphs are sentence-punctuation-normalized and space-joined (not a
  hardcoded Russian conjunction — the model can reply in any language).
  Output is plain text, safe to feed straight into TTS.

**Call-site wiring**:
- *Voice* — `agent_loop.go`. Add `voiceText(text) = ToVoiceText(Parse(text))`.
  `speakChunks` keeps publishing raw text to `/ws/logs` (a human should see
  real markdown there) but calls `o.speakText(ctx, voiceText(chunk))` —
  this alone covers the live `ha_assist` stream. `executeTool`'s
  `speak_reply` branch strips `args.Text` once at the top and uses the
  stripped value in **both** its `SpeakTo`/`speakText` branches (today
  `SpeakTo` bypasses `speakText` entirely — closing that gap too).
  **Known trade-off, flagged for sign-off**: `tts.Accumulator` cuts on
  sentence boundaries with zero markdown awareness, so a bold/link span
  *can* straddle two live-streamed chunks; stripping is done independently
  per chunk (not buffered/re-parsed as one whole reply, which would kill
  live-stream responsiveness), so a straddling span degrades to a stray
  literal `**`/`_` character rather than breaking anything — acceptable
  given normal voice replies are capped at ~100 chars by the system prompt
  already, but worth confirming is acceptable before implementing.
  **Decided**: `InputResponse.Reply` itself is also voice-stripped for
  `ha_assist`/`scheduled` — a "voice-classified" source's HTTP reply is
  treated as equivalent to what gets spoken, same transformer, no
  exceptions. This also means these two sources stop getting a
  `appendDownloadFootnotes` mention at all (per the original ask: voice
  doesn't need attachments) — only `telegram` keeps the footnote.
  Concretely, where `orchestrator.go` currently calls
  `appendDownloadFootnotes(finalText, control.downloadedFiles, req.Source)`
  to build `Reply`, this becomes a source switch:
  ```go
  var reply string
  switch req.Source {
  case users.SourceHAAssist, users.SourceScheduled:
      reply = voiceText(finalText) // same transformer used for TTS — no footnote
  default: // webUISource, telegram, anything else
      reply = appendDownloadFootnotes(finalText, control.downloadedFiles, req.Source)
  }
  ```
  Telegram's own send path still calls `replyformat.Parse(resp.Reply)` on
  this — the footnote text (plain, no markdown syntax) just becomes an
  ordinary paragraph block, so this composes without any special-casing on
  the Telegram side.
- *Telegram* — new `Client.SendHTML(ctx, chatID, blocks)` in
  `internal/telegram/client.go` (alongside the existing `SendMessage`, kept
  for Miranda's own static markdown-free strings) and `Sender.SendHTMLToUser`
  in `sender.go`, both reusing the existing `maxMessageChars`
  constant/`ToTelegramHTMLChunks`. Two call-site swaps:
  `internal/httpapi/telegram.go`'s webhook success-reply send, and
  `agent_loop.go`'s `send_telegram` tool handler.

**System prompt** (`internal/config/config.go`, `Default().Agent.SystemPrompt`):
add a `## Форматирование` section (after `## Ограничения длины`) telling the
model it may use `**bold**`/`*italic*`/`` `code` ``/`[label](url)`/`- list`
when it genuinely helps (multi-step instructions, option lists, source
links) — not in short voice replies — and that headers/quotes/tables/images
aren't supported. Without this the parser has nothing to parse in practice.

**Tests**: table-driven `parse_test.go` (one case per construct + the
list-vs-italic ambiguity + malformed-markup degradation + mixed
paragraph/list chunks), `telegram_test.go` (per-construct HTML + escaping +
the block-straddling chunk test), `voice_test.go` (per-construct stripping +
"URL never appears in output" + list/paragraph joining). Extend existing
`internal/telegram/client_test.go`/`sender_test.go` (mirroring
`TestSendMessage_PostsToCorrectMethodAndChat`/`TestSender_SendToUser_KnownChatSendsMessage`)
for the HTML send path with `parse_mode` asserted. Extend
`internal/httpapi/orchestrator_test.go` with a new markdown-containing
`speak_reply` case (existing speak tests around line 492-560 all use
plain text today, so they don't exercise the new stripping) and a
`InputResponse.Blocks` assertion. Extend
`internal/webui/webui_test.go`'s `TestHandleDialogMessages_ReturnsMessagesJSON`
to assert the new `blocks` field.

## Workstream B — vendor lit-html, migrate `chat.js`

**Vendoring** (`internal/webui/static/js/vendor/lit-html/`): unlike
`json-formatter-js` (one pre-built `.mjs` file), lit-html's own npm dist is
several small ESM files with relative imports among themselves, plus a
`directives/unsafe-html.js` this plan needs (see below). Recommended:
fetch a single flattened ESM bundle via a bundling CDN (e.g. `esm.sh`'s
`+esm`) at implementation time and commit that one file — closer to the
existing precedent's "one self-contained file" shape than vendoring the raw
multi-file npm dist. Requires network access not available during planning;
also needs verifying lit-html's core has zero further runtime dependencies.
Include a `LICENSE` file and a header comment mirroring
`json-formatter.mjs:1-30` (source URL, package+version, license, why
vendored, "re-vendor to update, don't hand-edit").

**New file** `internal/webui/static/js/segment-template.js` — exports
`blocksTemplate(blocks)`, mapping each `Block`/`Segment` to a lit-html
`html\`...\`` template (`<strong>`/`<em>`/`<code>`/`<a>`/`<ul><li>`/`<p>`).
Every interpolated segment's `text` is auto-escaped by lit-html by
default — the same trust boundary the current `textContent`-only rule
enforces, now enforced by the library instead of by hand.

**`chat.js` conversion** — six functions convert to `html\`...\`` +
`render()`: `bubble()`, `errorBubble()`, `emptyState()`, `skeleton()`,
`typingIndicator()`, `buildAttachChip()`'s initial shell. Everything else
(the `rendered` Map, `pendingUserKey`, `renderGeneration`, WS handling,
upload XHR logic, `mount()`/`unmount()`) is untouched — this is a
rendering-layer swap, not a rearchitecture. Messages still get appended one
at a time (never a full-list re-render): each per-message wrapper `<div>`
is created exactly as today, then `render(blocksTemplate(...), wrapperDiv)`
populates its contents once.

- `bubble()`: when `message.blocks` is present and non-empty, render via
  `blocksTemplate`; otherwise fall back to the existing
  `renderInlineText()` path (covers user messages, which never get
  server-computed `blocks`, and any WS-race edge case). `renderInlineText`
  itself is **not** forked or deprecated — `history.js` (not migrating)
  keeps using it exactly as today.
- `downloadChip()`/`attachmentChip()` (downloads.js) need **no changes** —
  they return real DOM `Node`s already, and lit-html accepts a `Node`
  directly as an interpolated child value.
- **Flagged integration risk**: `icon()` (icons.js) returns a raw SVG
  *string* (confirmed by reading the file), currently safe only because
  every call site uses `innerHTML =`. Inside a lit-html template,
  `${icon(...)}` would be auto-escaped like any other string (showing
  literal `&lt;svg&gt;...` text) unless wrapped in lit-html's `unsafeHTML()`
  directive — safe to do only because `icon()`'s output is Miranda's own
  hardcoded registry, never user-fed. Every chat.js call site that embeds
  an icon in a new template needs this wrap; easy to forget, visually
  obvious if missed.
- `mount()`'s own big static composer/scroll-area shell (lines 613-656)
  stays as a plain `innerHTML` template — it's built once and never
  patched again, so converting it buys nothing and wasn't part of the six
  functions in scope.

**No automated JS test coverage exists in this repo** (no `package.json`,
no test runner) — Workstream B's verification is manual via the `run`
skill: send a reply containing every construct and visually confirm
rendering; reload the chat screen (exercises the same `blocksTemplate` path
through `GET /api/dialogs/{id}`) and confirm it matches; exercise the
file-attach progress/thumbnail/remove flow (confirms `buildAttachChip`'s
imperative follow-up mutations still work against lit-html-rendered DOM);
trigger an error bubble and confirm the `@click` retry binding works;
spot-check `history.js` is unaffected (pure regression check, since neither
file it depends on changed).

## Implementation order

1. `internal/replyformat` — types, `Parse`, all three renderers, full unit
   tests. Self-contained.
2. Telegram wiring + tests.
3. Voice wiring + tests.
4. Web JSON wiring (`InputResponse.Blocks`, `ChatEvent`/`publishChatMessage`,
   `webui.go`'s `messageView`) + tests — Workstream B needs this data shape.
5. System prompt change.
6. `go build && go vet && go test ./...` full pass before touching frontend.
7. Vendor lit-html (network access required).
8. `segment-template.js`.
9. `chat.js` conversion (the six functions + `icon()`/`unsafeHTML()` care).
10. Manual end-to-end verification via the `run` skill (web rendering,
    Telegram send, voice speech) — no automated frontend regression net.

## Open risks / sign-off needed before implementation

1. Voice + live streaming: a markdown span can straddle two TTS chunk
   boundaries; recommended fix accepts a rare stray-delimiter artifact
   rather than buffering the whole reply (which would kill live-stream
   responsiveness).
2. lit-html's file layout / zero-runtime-dependency claim is unverified
   (no network access during planning) — the "fetch one flattened bundle"
   approach is specifically chosen to de-risk this.
3. `icon()` + `unsafeHTML()` discipline in chat.js is manual, not enforced
   by any lint/check.
4. Telegram HTML chunking's tag-straddling fallback is the trickiest
   correctness requirement in Workstream A — needs a dedicated test before
   trusting it against a real bot.
5. No automated regression coverage for the chat.js rendering change
   (consistent with this repo's no-build-step stance, but a real asymmetry
   versus Workstream A's Go test coverage).

Resolved during planning: `InputResponse.Reply` for `ha_assist`/`scheduled`
is voice-stripped via the same transformer as TTS (see Workstream A's call-
site wiring) — a voice-classified source's HTTP reply is treated as
equivalent to what gets spoken.
