# Домашний голосовой ассистент — саммари проекта

*Цель: заменить Яндекс Алису на кастомную систему (Claude/любая LLM + Home Assistant + локальный голосовой пайплайн), с полным контролем над тулами, памятью и приватностью.*

---

## 1. Общая архитектура (актуальное состояние на конец этой сессии)

```
┌──────────────────────────────────────────────────┐
│                  Home Assistant                    │
│                                                      │
│  Voice PE / Satellite1 ──wake word──> Assist Pipeline │
│         │                                  │          │
│         │ STT (Whisper, Wyoming)           │          │
│         ▼                                  ▼          │
│  Speaker Recognition (Resemblyzer) ──> [Тонкий Conversation Agent] │
│         │                                  │          │
│         │ user_id                          │ HTTP POST│
└─────────┼──────────────────────────────────┼──────────┘
          │                                  ▼
          │                    ┌────────────────────────┐
          │                    │   Agent Service (новый)  │
          │                    │  - LiteLLM router         │
          │                    │  - память/история по user_id │
          │                    │  - MCP-клиент (несколько)│
          │                    └────────────┬────────────┘
          │                                 │ MCP (Streamable HTTP)
          │                                 ▼
          │                    ┌────────────────────────┐
          │                    │   HA MCP Server           │  /api/mcp
          │                    │  (официальный ИЛИ ha-mcp) │
          │                    │  = все физические устройства│
          │                    └────────────────────────┘
          │                                 │
          │                    ┌────────────┴────────────┐
          │                    │  Прочие MCP-серверы (вне HA) │
          │                    │  - noolite-mcp (PHP, direct)│
          │                    │  - фитнес-приложение и т.д. │
          │                    └────────────────────────┘
          ▼
   Voice PE озвучивает через штатный TTS-шаг pipeline (Zvukogram)
   Яндекс.Станции — отдельный канал через media_player.play_media (см. раздел 7)
```

**Ключевой архитектурный принцип (финальное решение этой сессии):** агент — это **отдельный сервис** (свой репозиторий/контейнер), НЕ custom_component внутри HA. HA — один из источников тулов (через MCP Server) и один из каналов ввода/вывода (через тонкий conversation agent), а не "дом", в котором живёт агент. Управление домом — не основная функция агента, а одна из многих.

## 2. Железо

| Компонент | Устройство | Роль |
|---|---|---|
| HA Core | Synology DS223 (Docker) или текущий dev-хост | Всегда включён, ARM, только оркестрация |
| STT/TTS/локальная LLM (кандидат) | MacBook Pro M4 (тест) → RTX 5080 PC (финал) | Wyoming Whisper, локальные модели |
| Голосовой сателлит | **Решение: Satellite1.1 Smart Speaker** (не официальный Voice PE) | Wake word, мультирум, свой 20Вт динамик |
| Управление светом | NooHub (noo.by), RF 433MHz, HTTP REST API | Через custom_component |
| Существующие колонки | 2× Яндекс.Станция | Доп. TTS-канал, мультирум, голосовые макросы (НЕ полноценный сателлит) |

### Почему Satellite1.1, а не Voice PE
- Voice PE: dual-mic XMOS XU316, включая крошечный встроенный динамик, нет Bluetooth Classic/A2DP (ESP32-S3 физически не поддерживает — только BLE)
- Satellite1.1: тот же класс чипов, но 4-микрофонный массив, полноценная 20-ваттная 2-полосная акустика, Snapcast-мультirum, Spotify Connect/AirPlay/YouTube Music, датчики (темп/влажность/presence через LD2450), разборный корпус
- Оговорка: полноценный 4-mic beamforming у Satellite1.1 на момент этой сессии ещё "в разработке" по словам самого производителя
- И Voice PE, и Satellite1.1 **не могут** выводить звук на Bluetooth-колонку (аппаратное ограничение ESP32-S3 — нет Bluetooth Classic/A2DP)

### Двойной wake word (свежая фича HA)
HA поддерживает 2 одновременных wake word на одном сателлите с разными pipeline — потенциально закрывает часть задачи роутинга "простое/локально vs сложное/Claude" на уровне прошивки, а не только программно. Требует поддержки в прошивке сателлита (несколько одновременных моделей `micro_wake_word` + репортинг какая сработала) — для Satellite1.1 не подтверждено на 100%, стоит проверить актуальный firmware changelog.

## 3. Написанные компоненты (все на GitHub, archer-developer)

### noolite-mcp (PHP, Docker)
MCP-сервер для NooHub API. `docker compose run --rm --no-deps mcp php server.php` как stdio-entrypoint. PHPStan level 8 + php-cs-fixer (Symfony style), pre-commit hooks. 11 тулов: get_devices, get_state, set_state, get_rooms, add_room, edit_room, get_device_settings, get_settings, get_scenarios, run_scenario, delete_scenario. Используется для прямого тестирования через Claude Code; в финальной voice-архитектуре HA дублирует эти устройства как entities.

### noolite-ha-integration (Python custom_component)
HA-интеграция для NooHub — устройства как полноценные entities (свет и т.д.). Ключевая доработка: **сериализация запросов через общий `asyncio.Lock`** + retry с задержкой на ошибку `device_busy` — потому что физический RF-хаб NooHub обрабатывает команды строго последовательно, а HA по умолчанию шлёт параллельные вызовы при групповых командах ("включи всё в зале").

### zvukogram-ha-integration (Python custom_component)
TTS-провайдер поверх API zvukogram.com (дешёвый, без геоблокировки, synchronous `api/text` для коротких фраз ≤1000 символов). Чанкинг длинных текстов с параллельным синтезом по чанкам.

### speaker-recognition (форк EuleMitKeule/speaker-recognition)
Resemblyzer-based распознавание говорящего, обогащает `context.user_id` в conversation pipeline. Внесённые фиксы:
1. **Параллелизация** STT (Whisper) и распознавания голоса — recognition запускается как только аудио-стрим исчерпан (`asyncio.create_task`), а не после того как Whisper закончит транскрибацию — экономит задержку.
2. **MIME-баг**: Python `mimetypes` отдаёт `.wav` как `audio/x-wav`, а не `audio/wav` — селектор фильтровал все WAV-файлы. Добавлено `audio/x-wav` в accept-лист.
3. **Путь к медиафайлам**: код использовал `hass.config.path("media")` (= `/config/media`), а реальный local-media root на Container-инсталляциях — отдельный смонтированный `/media` (через `hass.config.media_dirs["local"]`). Добавлена явная проверка `exists()`.
4. **Протухший кэш ConfigEntry**: `recognition` property кэшировал ссылку на `ConfigEntry` при `__init__`, а reload (например при обновлении voice_samples) пересоздаёт объект — кэш становился невалидным. Исправлено на поиск entry заново при каждом обращении.
5. **Неверное имя поля Pydantic**: `result.users_trained` не существует, реальное поле — `result.count`. Ошибка ломала `async_setup_main_entry` целиком (поскольку `entry.runtime_data = recognition` присваивался ПОСЛЕ вызова `async_train()`, крашащегося раньше).
6. **Новая фича — STT confidence gate**: если распознанная уверенность ниже порога (`CONF_STT_MIN_CONFIDENCE`, дефолт 0.6, настраивается слайдером) — STT возвращает `SpeechResult(None, ERROR)` вместо реальной транскрипции, обрывая пайплайн ДО того как текст доходит до LLM (экономит деньги на шумовых срабатываниях). Fail-open: если recognition service недоступен — не блокируем пайплайн.

**Инфраструктурный баг (вне custom_component, сам Docker-сервис)**: `Dockerfile` сервиса задаёт `EMBEDDINGS_DIR=/data/embeddings`, а не `/app/embeddings` — volume в `docker-compose.yml` нужно мапить именно на `/data/embeddings`, иначе обученные эмбеддинги живут только в writable-слое контейнера и теряются при пересоздании.

**Известный (непроверенный) баг**: селектор голосовых сэмплов в UI поддерживает `multiple=True`, но код обработки похоже ожидает один медиа-объект, а не список — не проверено на практике, тестировать сначала с одним сэмплом на человека.

## 4. Голосовой пайплайн — практические решения

### TTS
- **Основной**: Zvukogram (дёшево, ~$0.01/1000 симв., без геоблокировки) — для Voice PE/Satellite1
- Яндекс SpeechKit — пробовали, региональные проблемы с оплатой из ЕС, отказались
- Silero — пробовали локально, качество не устроило
- Piper — базовый локальный вариант, качество хуже Yandex/Zvukogram

### STT
- Wyoming Whisper (`small` модель), тестируется на M4 перед финальным размещением

### Тестирование wake word без реального железа
- `wyoming-satellite` — **архивирован 27 января 2026**, заменён на `OHF-Voice/linux-voice-assistant` (ESPHome-протокол)
- Тестирование на Mac ограничено — Docker Desktop на macOS не даёт прямого доступа к аудио-железу хоста; для полноценного теста нужен настоящий Linux
- Быстрый тест самой wake-word модели — `openwakeword` + `sounddevice` напрямую в Python, без Docker/HA
- Пайплайн STT→LLM→TTS без wake word тестируется через браузерную кнопку "Try" в Settings → Voice Assistants

### Запись голосовых сэмплов для speaker recognition
- Формат: строго 16-bit PCM mono WAV, 16000 Hz (сервер не декодирует контейнер — читает сырые байты как PCM)
- `ffmpeg -i input.m4a -ar 16000 -ac 1 -c:a pcm_s16le output.wav`
- **Лучший способ**: включить `debug_recording_dir` в `assist_pipeline:` конфиге HA и записать сэмпл через сам Voice PE/Satellite1 — тогда сэмпл проходит через тот же акустический фронтенд (AEC/шумоподавление), что и реальное использование, плюс сразу в нужном формате. Не забыть выключить debug recording после (иначе HA пишет на диск каждую голосовую команду постоянно).
- Debug recording сохраняет отдельный файл на каждую фразу — для сэмпла 10-20 сек нужно либо сказать длинную фразу целиком, либо склеить несколько файлов через `ffmpeg -i "concat:f1.wav|f2.wav" -acodec copy out.wav`

### Фоновый шум / TV
- STT confidence gate (см. раздел 3) отсекает голоса, не совпадающие ни с одним обученным профилем — TV-голоса не совпадут ни с кем
- Физическое размещение сателлита ближе к говорящему, чем к источнику шума, остаётся самым эффективным и дешёвым способом

## 6. Архитектура LLM-агента (решение этой сессии, детали — в Claude Code)

### Требования пользователя
- Model-agnostic: любая OpenAI-tool-compatible модель (Qwen, Gemini, локальные модели), включая комбинирование по задаче/доступности
- Claude — дорого для постоянного личного использования, но качество эталонное для сложных случаев
- Собственная память и история диалогов **по пользователю** (не по conversation_id), критично важно
- Множество разных тулов, часть из которых пишутся с нуля
- Управление домом —一 из многих функций, не главная
- Использование на двоих (муж + жена), с индивидуальной памятью на человека (через speaker recognition → user_id)

### Решения
- **LiteLLM** (Proxy или SDK) — unified OpenAI-совместимый интерфейс поверх Anthropic/OpenAI/Gemini/локальных серверов (Ollama/vLLM), встроенный Router с fallback-цепочками — закрывает "любая модель + комбинирование по доступности" без велосипеда
- **Разделение тулов**:
  - Всё физическое оборудование дома → через HA (существующие/будущие HA-интеграции), доступно агенту через **HA MCP Server** (`/api/mcp`, Streamable HTTP, Long-Lived Access Token)
  - Всё нефизическое (фитнес-приложение, календарь и т.п.) → отдельные MCP-серверы, подключаемые к агенту напрямую, в обход HA
  - Официальный `mcp_server` в HA даёт лишь ограниченный набор тулов (тот же, что видит голосовой Assist); для более широкого доступа (автоматизации, дашборды, аддоны) рассмотреть community-проект `homeassistant-ai/ha-mcp` (95+ тулов, активно поддерживается, может работать вне HA — подходит для Container-инсталляции)
  - `noolite-mcp` (свой PHP-сервер) остаётся как опциональный прямой путь в обход HA (быстрее, но дублирует то, что уже доступно через HA MCP)
- **Голосовой вход**: внутри HA — максимально тонкая `ConversationEntity`, которая просто форвардит текст+user_id+conversation_id по HTTP в Agent Service и возвращает ответ; никакой LLM-логики внутри HA
- **Память**: полноценная БД (SQLite для старта) в Agent Service, ключ — `user_id` от speaker recognition, а не эфемерный `conversation_id` из HA chat_log
- **Streaming TTS для Яндекс-колонок**: раз агент теперь свой сервис — нарезка стрима на предложения (regex по `.!?…`, макс. 100 символов на чанк из-за ограничения Яндекс API) и последовательная отправка на колонку с ожиданием `idle`-состояния перед следующим чанком реализуется прямо в сервисе, без необходимости форкать HA-интеграцию Anthropic

### Открытые вопросы для проработки в Claude Code
- Схема БД для памяти/истории (по user_id)
- Конкретный список MCP-серверов для конфигурации (`mcp_servers.yaml`: URL/токен/вкл-выкл на каждый)
- Соглашение об именовании тулов при большом числе MCP-источников (префиксы по домену)
- Логика роутинга между моделями (явный tool `escalate_to_claude` vs LiteLLM Router fallback по ошибке/уверенности)
- Синхронизация состояния media_player для Яндекс-колонок (`async_track_state_change_event` на переход в `idle` перед следующим TTS-чанком)

## 7. Яндекс.Станции — интеграция (AlexxIT/YandexStation)

- Установлена, 2 колонки видны как `media_player` entities, локальный режим работает
- **TTS через `media_content_type: text`** (НЕ `dialog`!) — `dialog` открывает микрофон станции после фразы для собственного распознавания Алисы, что конфликтует с нашим голосовым пайплайном и может привести к нежелательным реакциям Алисы на посторонние звуки
- Лимит 100 символов подтверждён как реальный даже в локальном режиме на практике (документация явно относит лимит только к облачному режиму, но по факту ограничение действует и в локальном)
- Это **НЕ замена** штатному TTS в Assist pipeline — Яндекс.Станция требует явный `entity_id` в каждом вызове (жёстко привязана к конкретной колонке), а не "сгенерируй файл для того, кто спросил" —架構urно несовместимо со стандартным TTS-слотом pipeline
- Реализация: отдельный канал — после получения ответа от conversation agent, отдельный шаг (в новом Agent Service) нарезает текст на чанки ≤100 симв. и шлёт на конкретную колонку через `media_player.play_media`
- Инструменты для управления колонками **не появляются в Assist автоматически** — нужно включить "Expose to Assist" на entities; появятся только базовые intents (пауза/громкость/переключение), фирменные фичи (TTS-эффекты, конкретные альбомы, настройки Алисы) нужно оборачивать в HA Scripts и тоже экспонировать
- **"Алиса как сателлит" — НЕ работает** для произвольной речи. Механизм "Получение команд от станции" требует заранее зарегистрированных в приложении Яндекса конкретных фраз-триггеров (сценарий "Фраза" → "Выполнить команду"), открытого STT-канала со свободной речью нет: *"нельзя узнать фразу, которую сказали колонке — можно узнать только фразу, которую колонка выполнила"*
- Обходные пути на случай блокировки Яндекса из региона уже встроены в интеграцию: смена домена (`yandex.com`), HTTP-прокси, отключение проверки SSL

### Возможность (не реализовано): мультирум-мост
YandexStation поддерживает трансляцию музыки с Яндекс-колонки на колонки других брендов (Chromecast/DLNA/Sonos/etc, включая потенциально Satellite1 если у него подходящая интеграция) — требует подписку Яндекс.Музыка.

### Яндекс.Музыка в HA
Есть `AlexxIT/YandexStation` (базовое проигрывание по ID трека/альбома) + `alryaz/hass-yandex-music-browser` (полноценный Media Browser UI, заявлена поддержка сторонних плееров вроде Kodi — намекает на возможность фида в произвольный media_player, не проверено с Satellite1). Неофициальный реверс-инжиниренный API — риски аналогичные SpeechKit (регион/стабильность).
