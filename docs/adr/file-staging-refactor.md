# Рефакторинг передачи файлов пользователя во внешние MCP-сервисы

> Статус: реализовано. Изначально написано в другой сессии (работа велась в
> `miranda-medical-card`) как предложение (§1) и передано сюда для
> реализации. Первая реализация (push/ре-стейджинг, см. §2) оказалась
> недостаточной при первой же боевой проверке и была заменена дизайном из
> §3 — этот документ описывает обе попытки, чтобы будущая сессия не
> наступила на те же грабли. Если что-то из описанного ниже разойдётся с
> кодом в будущем — верь коду, не этому файлу.

---

## 1. Проблема, которая это вызвала

Живой тест: пользователь попросил Miranda "загрузи файл в медкарту" (новый MCP-сервис `miranda-medical-card`, инструмент `medical.upload_file`, параметр `data` — файл в base64 прямо в аргументах tool-вызова).

Фактически произошло: Miranda (backend) застейджила файл в `code_exec_sandbox` (как это происходило для любого вложения на тот момент), LLM (`gemini-lite`) честно попыталась прочитать файл внутри sandbox-сессии, но когда дошло до вызова `medical_card_medical.upload_file`, у неё не было способа получить настоящий base64 400КБ PDF в свой собственный текстовый вывод — и она **сгаллюцинировала** правдоподобно выглядящий, но полностью не настоящий PDF-контент вместо него. `medical.upload_file` на стороне medical-card корректно отклонил это как невалидный base64.

Корень проблемы: **передача байт между сервисами — механическая задача, а не задача, требующая понимания языка**, а тогда единственный способ доставить содержимое файла в сторонний MCP-сервис был — заставить LLM самостоятельно провести его через свой собственный текстовый контекст. На файлах в несколько сотен КБ (обычный размер сканов медицинских документов) это в принципе ненадёжно, независимо от модели.

## 2. Первая попытка (push/ре-стейджинг) — реализована и отклонена

Идея: backend перехватывает исходящий tool-вызов и сам делает `POST /files` на целевой сервис прямо перед пересылкой, подставляя реальный `fileId` вместо локального ID вместо того, чтобы просить модель передать байты. Реализация: конфиг `MCPServer.FileStagingAllowed`/`FileIDArgName` (по аналогии с уже существующим `EncryptionKeyAllowed`/`EncryptionKeyArgName`, см. `../../internal/config/config.go`), новый пакет `internal/filestage` (TTL-кэш `(conversationID, localFileID, serverName) → remoteFileID`), метод `Orchestrator.restageFileArg` в `../../internal/httpapi/agent_loop.go`, перехватывающий вызов в `executeTool` тем же способом, что и `setEncryptionKeyArg` уже перехватывает вызовы для инъекции ключа шифрования.

**Почему это не сработало при первой же боевой проверке.** `restageFileArg` перехватывает только вызовы, где модель действительно передала распознаваемый аргумент (`target.ArgName`, например `fileId`) тому тулу, который на это рассчитан (`medical_card_medical.upload_document`). Но ничто не мешало модели вместо этого вызвать *другой* тул того же сервера, который принимает сырые байты напрямую — `medical_card_medical.upload_file` с параметром `data`. Первая же реальная попытка ("отправь в мед карту") воспроизвела исходный баг из §1 один в один: модель вызвала именно `medical_card_medical.upload_file(data=<hallucinated base64>)`, получив от medical-card `INVALID_FILE: data must be non-empty valid base64` — байты из `../../logs/llm.log`:

```
"Name": "medical_card_medical.upload_file",
"Arguments": "{...,\"data\":\"JVBERi0xLjcKJeLjz9MKNCAw obj\\nPDwgL1R5cGUgL1BhZ2Ug...\",...}"
→ error: {"code":"INVALID_FILE","message":"data must be non-empty valid base64"}
```

Первая заплатка — `rawFileBytesArgName`, эвристика, распознающая "похоже на base64" по низкой доле пробелов + высокой доле base64-алфавита в строковом аргументе, отклоняющая такой вызов до отправки на сервер. Она сработала бы, но её справедливо признали недостаточно чистым решением: это вероятностный детектор поверх симптома, а не структурное устранение причины — ничто не мешало бы модели найти способ обойти эвристику, и `medical_card_medical.upload_file` как тул, принимающий сырые байты, продолжал бы существовать и быть доступным модели.

**Урок**: пока в списке доступных модели тулов есть хоть один, который в принципе принимает файл как параметр (байты или что угодно, что нужно "составить" самой модели), проблема из §1 не решена структурно — не важно, что где-то ещё есть "правильный" путь через `fileId`.

## 3. Финальный дизайн: Miranda хостит файл, сервисы сами его забирают по URI

Вместо того чтобы решать, **куда** пушить байты, и пытаться поймать модель на попытке обойти это — Miranda вообще перестаёт куда-либо посылать байты сама. Она хостит файл у себя и выдаёт модели **URI**, а не непрозрачный ID. Любой тул на любом сервисе, которому нужны байты файла, сам делает обычный HTTP GET по этому адресу. Это устраняет весь класс бага структурно: не остаётся ни одного тула, принимающего сырые байты как аргумент (`upload_file`/`upload_document` на стороне sandbox и medical-card переделываются, в своих репозиториях, чтобы принимать `fileUri` и самим его выкачивать) — значит, модели физически некуда галлюцинировать байты.

**Прецедент этого же класса задачи уже был в кодовой базе** — `../../internal/tts/httpserve.go`'s `GET /tts-audio/{filename}` уже отдаёт LAN-устройству (Yandex-станции) ресурс по непредсказуемому ключу, **без отдельной авторизации вообще** — случайность самого ключа и есть credential — и `config.TTSConfig`'s `gemini_tts.public_base_url` уже существует именно для "адреса, по которому LAN-устройство может достучаться до файлового роута Miranda" (`internal/tts/gemini.go:110,218`). Этот дизайн переиспользует оба паттерна, а не изобретает новые.

### 3.1 Как это работает

1. **`POST /api/upload`** (`../../internal/httpapi/upload.go`, `handleUpload`) больше никуда не проксирует байты. Генерирует свой ID (`attachments.NewFileID()` — 24 случайных байта, hex, тот же паттерн, что уже использует `internal/telegram.RandomSecret`), кладёт `Data` (буферится теперь для *любого* вложения, не только картинок/текста для инлайна) в `internal/attachments.Store` и возвращает этот ID клиенту как раньше.
2. **`GET /files/{id}`** (новый роут, `handleFilesServe`) — намеренно **без авторизации**, тот же прецедент, что `/tts-audio/`: смотрит `id` в `attachStore`, отдаёт байты с правильным `Content-Type`/`Content-Disposition`, 404 если не найден. Это адрес, по которому внешний сервис забирает файл — не то же самое, что уже существующий, авторизованный `GET /api/files/{file_id}` (`handleDownload`), который отдаёт файл в браузер пользователя для направления скачивания (сервис → пользователь), не тронут этим рефакторингом.
3. **`processAttachments`** (`../../internal/httpapi/attachments.go`) строит `fileURI = strings.TrimRight(PublicBaseURL, "/") + "/files/" + fileID` и для **каждого** вложения (не только бинарных — картинка/текст тоже инлайнятся как раньше для vision/контекста, но заодно получают URI на случай, если модели нужно передать сам файл, а не только его содержимое, куда-то ещё) добавляет структурный `<attachment>{json}</attachment>`-маркер (`appendAttachmentMarker`) с этим URI и человекочитаемой инструкцией внутри JSON — см. §3.3, почему это маркер, а не просто текст в сообщении. Для бинарных/PDF-файлов, где инлайнить нечего, это единственная информация: явная инструкция никогда не пытаться передать содержимое файла в аргументах вызова, а передавать именно этот адрес.
4. **`config.FileUploadConfig.PublicBaseURL`** (`public_base_url` в YAML) — базовый адрес, по которому сторонние сервисы могут достучаться до `GET /files/{id}`, зеркально `gemini_tts.public_base_url`. Обязателен при `file_upload.enabled: true` — `../../cmd/miranda` падает при старте, если он не задан (та же логика, что уже проверяет `gemini_tts.PublicBaseURL` в момент использования).

### 3.2 Что осталось от предыдущей попытки

Ничего специфичного для push/ре-стейджинга — `internal/filestage`, `restageFileArg`, `rawFileBytesArgName`, `FileStagingAllowed`/`FileIDArgName` полностью удалены. Единственное, что уже существовало и было переиспользовано без изменений — `MCPServer.FilesEndpoint()`/`Config.SandboxFilesURL()` (нужны только для скачивания, не для загрузки, см. §5). *(Обновление после §6: `Config.SandboxFilesURL()` тоже удалена — скачивание теперь идёт через единый `Config.FileExposingServers()` для всех серверов, sandbox включительно.)*

### 3.3 Третий инцидент: веб-UI показал служебный текст вместо чипа файла

Первая версия §3.1 (та, что попала в первый деплой этого дизайна) писала для бинарных вложений человекочитаемое предложение прямо в текст сообщения — то же место, откуда `../../internal/webui/static/js/screens/chat.js`'s `extractFileAttachments` регэкспом вырезал текст и рисовал вместо него чип. Регэксп был жёстко завязан на *точную* старую формулировку ("... загружен в sandbox ... программно."). Как только формулировка сменилась на "доступен по адресу ..." — регэксп перестал матчиться, чип пропал, а сырой служебный текст с URL утёк прямо в пузырь чата. То же самое произошло бы для картинок/текстовых файлов на следующем сообщении: к их плейсхолдерам добавилось предложение "также доступен по адресу ...", которое существующие регэкспы тоже не матчили.

Фикс, зеркально уже существующему `<download>{json}</download>`-маркеру (`appendDownloadMarkers` в `agent_loop.go`, `extractDownloadBlocks` в `downloads.js`): `processAttachments` теперь для каждого вложения добавляет структурный, версионированный `<attachment>{json}</attachment>`-маркер (`filename`, `mime_type`, `size_bytes`, `uri`, `note`) — новая функция `appendAttachmentMarker`. Клиент (`extractAttachmentBlocks`, вынесена в общий `downloads.js`, используется и `chat.js`, и `history.js` — заодно чип теперь рисуется и в истории, чего раньше не было вообще) парсит только границы тега и JSON внутри, не завязываясь на конкретные слова — `note` внутри маркера остаётся читаемым для модели текстом, но клиент его не парсит вообще, только берёт `filename`/`size_bytes` для чипа.

**Урок**: то же самое, что уже отражено в прецеденте с `<download>` — любой server-emitted текст, который одновременно (а) должен остаться понятным модели при повторном воспроизведении истории и (б) должен быть скрыт от человека в UI и заменён виджетом, обязан идти через структурный маркер с самого начала, а не через regex, завязанный на конкретную формулировку.

## 4. Контракт для sandbox и medical-card (не реализовано в этом репозитории — точная спецификация для той сессии)

- **`miranda-code-execution-sandbox`**: убрать `POST /files` (больше не принимает пуш-загрузки; `GET /files/{id}` для скачивания результатов — не трогать, вне скоупа). Схема тула `upload_file` меняется с `file_id` (раньше — sandbox-местный ID из `POST /files`) на `fileUri`; обработчик сам делает HTTP GET по этому адресу и копирует байты в контейнер сессии — дальше без изменений.
- **`miranda-medical-card`**: убрать `POST /files` (было в §4 старой версии этого документа) целиком — и, что важно, убрать `medical.upload_file(data=...)` тоже, поскольку это и есть тул, вызвавший оба инцидента (§1 и §2). Схема `medical.upload_document` меняется с `fileId` на `fileUri`; обработчик сам скачивает файл и прогоняет через тот же OCR/pipeline, что и сейчас.
- Оба сервиса обращаются к новому, не требующему авторизации `GET {public_base_url}/files/{id}` Miranda — никакого токена настраивать не нужно, в отличие от прежнего `POST /files`, который требовал их собственную bearer-проверку.

## 6. §5 закрыт: скачивание обратно пользователю обобщено под произвольный URI

Триггер: `medical_card_medical.get_document` возвращает `fileUri`, указывающий на внутренний адрес самого MCP-сервера (`https://127.0.0.1:8791/files/{id}`), защищённый тем же bearer-токеном, что и `/mcp`. Модель просто вставляла этот URI в свой ответ verbatim — ссылка была одновременно недостижима из браузера пользователя (внутренний хост) и не авторизована (нет токена). Старый механизм (`Orchestrator.SetSandboxDownload`) не помогал: он матчил ровно один захардкоженный тул (`download_file`) по имени, а здесь файл возвращает произвольный тул (`get_document`) как поле обычного JSON-ответа.

Первая версия решения добавила **второй**, generic и opt-in путь параллельно старому sandbox-специфичному (`SetSandboxDownload` — парсинг `file_id: ...` текстом — оставался нетронутым, потому что его формат ответа, голый id, не URL, не покрывался URL-детектором). По прямому запросу «хочу одну реализацию фичи для всех сервисов» старый путь убран целиком, а `detectRemoteFileLinks` расширен так, чтобы покрывать и его формат — теперь это единственный механизм:

- `config.MCPServer.ExposeFiles` (`expose_files: true`) явно помечает сервер как "его собственные ссылки на файлы можно перехватывать и проксировать" — **включая сам sandbox**, у которого больше нет отдельного пути. Без этого флага результат тула вообще не сканируется — сервер, который никто не whitelist'ил, не может заставить backend куда-то проксировать произвольный URL (это был бы SSRF: скомпрометированный/сбойный MCP-сервер мог бы вернуть в JSON-поле ссылку на что угодно во внутренней сети, и Miranda добросовестно бы её зафетчила и отдала в браузер).
- `Config.FileExposingServers()` собирает `FilesEndpoint()` (тот же `/mcp` → `/files` конвеншн) для каждого такого сервера → `Orchestrator.SetFileExposingServers(servers, recordTTL)` — единственный сеттер, `SetSandboxDownload` удалён вместе с полями `sandboxDownloadToolName`/`sandboxFilesURL`/`sandboxFilesToken` на `Orchestrator` и `Config.SandboxFilesURL()`/`FileUploadConfig.SandboxMCPServerName` в конфиге.
- `executeTool` (`agent_loop.go`) после любого вызова к опознанному серверу (`mcp.Manager.ServerForTool`) сканирует сырой результат тула на URL с префиксом этого сервера's `FilesEndpoint` (`detectRemoteFileLinks`) — только префикс матчит, никогда произвольный URL из ответа. Для каждого найденного URL: минтится новый `attachments.FileID`, кладётся `Record{RemoteURL, RemoteToken}`, и в финальный ответ детерминированно добавляется `<download>{...}</download>`-маркер (`control.downloadedFiles`/`appendDownloadMarkers`).
- Метаданные (имя файла/mime/размер) — best-effort, теперь двумя способами внутри одной функции, в зависимости от формы результата:
  - результат — JSON (`medical.get_document`): соседнее поле (`title`/`filename`/`name`/`size_bytes`/`mime_type`/...) в том же объекте, где стоит найденный URL (`findSiblingObject` + `stringSiblingField`/`int64SiblingField`);
  - результат — плоский текст `key: value` (sandbox-формат `download_file`): та же логика по строкам (`keyValueStringField`/`keyValueInt64Field`), с теми же списками ключей.
  Не нашли — чип показывается без имени/размера, а не с угаданным неверным.
- `GET /api/files/{file_id}` (`handleDownload`) проксирует по `Record.RemoteURL`/`Record.RemoteToken` из самой записи, а не по единственному глобальному значению на `Server` — это и раньше позволяло проксировать несколько сервисов одновременно, теперь используется без исключений для всех, включая sandbox.

**Важное следствие, уже закрыто**: поскольку `download_file` больше не имеет своего кода на стороне Miranda, песочница обязана вернуть полноценный `file_uri` в своём plain-text результате — без этого её скачивания не проксировались бы. Со стороны `miranda-code-execution-sandbox`: `download_file` теперь возвращает `file_uri` (`<public_base_url>/files/<id>`, где `public_base_url` — новое, отдельное от MCP-адреса поле конфига `config.Config.PublicBaseURL`, специально **не** завязанное на суффикс `/mcp` — см. её собственный CLAUDE.md/README) поверх уже существовавших `file_id`/`filename`/`size_bytes`/`mime_type` строк, не ломая их. Со стороны Miranda: `detectRemoteFileLinks` изначально умел читать метаданные только из JSON-соседей — для sandbox-формата (`file_id: ...\nfile_uri: ...\n...`, не JSON) этого было недостаточно, поэтому добавлен `keyValueStringField`/`keyValueInt64Field` — тот же список ключей (`filenameKeys`/`mimeTypeKeys`/`sizeBytesKeys`), но читающий `"key: value"`-строки вместо полей JSON-объекта.

**Урок**: если возвращать из тула сразу полный `fileUri` (а не голый id, который вызывающая сторона обязана как-то реконструировать в адрес), детектирование на стороне Miranda становится проще и надёжнее — не нужно знать конвенцию путей конкретного сервиса, достаточно проверить префикс. `miranda-medical-card` соответствовал этому контракту с самого начала (JSON); `miranda-code-execution-sandbox` был на голом `file_id` и потребовал изменений по обе стороны — оба теперь закрыты.
