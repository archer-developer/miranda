# Напоминания как отдельная сущность (`create_reminder` vs `create_scheduled_task`)

> Статус: реализовано (2026-09-12). Ссылки на строки ниже соответствуют
> состоянию репозитория на момент написания документа и могли разойтись с
> кодом с тех пор — верь коду, не этому файлу.

## 1. Проблема

`internal/schedule` хранит произвольный текст (`Task.Prompt`), который в
момент срабатывания заново прогоняется через полный агентный цикл —
`Orchestrator.RunScheduledTasks` (`../../internal/agent_loop/schedule.go:36-108`)
строит `InputRequest{Source: users.SourceScheduled, UserID, Text:
task.Prompt}` и вызывает `Handle` ровно так же, как если бы это сообщение
только что напечатал пользователь.

Это ломается на самом частом случае использования — простом напоминании.
Пользователь говорит «напомни мне в 22:00 полить кактус»; модель кладёт в
`Prompt` что-то вроде «напомни полить кактус» — повелительное предложение,
адресованное самой себе. В 22:00 этот текст реплеится в `Handle` как живое
сообщение пользователя, модель видит императив «напомни...» и добросовестно
делает то, что там написано — снова вызывает `create_scheduled_task`.
Получается бесконечный цикл пересоздания напоминания вместо однократного
уведомления «пора полить кактус».

Усугубляющие факторы:

- Описание `create_scheduled_task` говорит модели, что промпт «replayed...
  exactly like a live message», но никак не предупреждает, что нельзя
  писать его в повелительной форме, обращённой к себе же.
- `RunScheduledTasks` полностью отбрасывает текст ответа `Handle`
  (`_, err := o.Handle(...)`) — единственный способ реально что-то донести
  до пользователя это явный вызов `speak_reply`/`send_telegram` внутри
  этого хода. При этом описание `speak_reply` прямо отговаривает модель
  вызывать его «by own initiative» — то есть штатный путь плохо
  приспособлен именно для нотификаций.
- `resolveConversation` (`../../internal/agent_loop/session.go:19-58`)
  привязан только к `userID`, а не к `Source` — если диалог, в котором
  создавалось напоминание, ещё не закрылся, реплей попадает в тот же
  диалог, где уже видна пара «user: напомни мне... → assistant:
  create_scheduled_task(...)», что подкрепляет повтор того же паттерна.

## 2. Решение: разделить «напоминание» и «плановую задачу»

Вместо того чтобы чинить формулировку промпта или пытаться объяснить модели
через system prompt «не повторяй это как новую команду» (ненадёжно — модель
всё ещё должна правильно понять контекст в моменте), разделяем два разных
по природе сценария на уровне механизма:

- **Напоминание** (`create_reminder`) — пассивное уведомление. Модель
  сохраняет только содержимое сообщения (`message`, например «Полить
  кактус» — не «напомни полить кактус») плюс время. При срабатывании оно
  **никогда не проходит через `Handle`** — доставляется напрямую, минуя
  агентный цикл целиком. Зациклиться структурно невозможно: раз не
  происходит ни одного хода модели, нечего реинтерпретировать.
- **Плановая задача** (`create_scheduled_task`) — как и раньше, для
  случаев, где в момент срабатывания реально нужно принять решение или
  вызвать тул («проверь в 22:00, заперта ли дверь, и если нет — запри»).
  Поведение и путь через `Handle` не меняются.

### 2.1 Модель данных (`internal/schedule/schedule.go`)

`Task` получает три новых поля:

```go
type Kind string

const (
    KindTask     Kind = "task"
    KindReminder Kind = "reminder"
)

type Task struct {
    // ... существующие поля без изменений ...

    Kind          Kind   // "task" (по умолчанию, в т.ч. для всех старых строк) или "reminder"
    OriginSource  string // InputRequest.Source в момент создания — определяет канал доставки
    AnnounceAloud bool   // Kind == KindReminder: озвучить принудительно, даже если origin не голосовой
}
```

Миграция — три `ALTER TABLE ... ADD COLUMN` через `ensureColumn` (паттерн
уже есть в `internal/history/history.go:301-328`, в `internal/schedule` его
пришлось завести отдельно, так как раньше пакет обходился одним
`CREATE TABLE IF NOT EXISTS`): `kind TEXT NOT NULL DEFAULT 'task'`,
`origin_source TEXT NOT NULL DEFAULT ''`, `announce_aloud INTEGER NOT NULL
DEFAULT 0`. `DEFAULT 'task'` на `ADD COLUMN` ретроактивно проставляет всем
уже существующим строкам `kind = 'task'` — ни одна ранее запланированная
задача не меняет поведения.

### 2.2 Правило доставки напоминания

При срабатывании (`RunScheduledTasks` в
`../../internal/agent_loop/schedule.go`, новая функция `deliverReminder`):

1. **Канал создания** (`OriginSource`, никогда не переопределяется
   `AnnounceAloud`):
   - `ha_assist` → озвучить через TTS (`o.speakText`);
   - `telegram` → отправить в Telegram (`o.telegram.SendToUser`, тот же
     прямой вызов в обход тул-цикла, что уже использует `oauth_authorize`,
     `../../internal/agent_loop/tool_dispatch.go:252-254`);
   - иначе (web/неизвестный источник) → дописать сообщение в историю
     диалога пользователя (`history.AppendMessage` + `publishChatMessage`),
     чтобы оно было видно в веб-UI.
2. **Всегда дополнительно** — Telegram, best-effort, если канал создания не
   был Telegram (чтобы не дублировать отправку).
3. **`AnnounceAloud`** — не переопределяет канал создания, а добавляет
   озвучку поверх него: напоминание, созданное в Telegram с
   `announce_aloud: true`, всё равно уходит в Telegram и, если это
   возможно, дополнительно озвучивается.

Ошибка на шаге 1 (канал создания) — это ошибка всей доставки
(`StatusError` в `scheduled_task_history`); ошибка на шаге 2
(дополнительный Telegram) — только предупреждение в лог, не влияет на
статус (пользователь без известного Telegram-чата не должен превращать
иначе успешное напоминание в ошибку).

### 2.3 Инструменты модели

- Новый `create_reminder`: `message` (обязательно, содержимое
  напоминания, НЕ команда себе), `run_at`/`schedule` (как у
  `create_scheduled_task`), `announce_aloud` (опционально).
- `create_scheduled_task`: поведение не меняется, только описание
  уточняется — явно отсылает к `create_reminder` для простых «напомни
  мне...» запросов и оставляет себя для случаев с принятием решения в
  момент срабатывания.
- `list_scheduled_tasks`: показывает `kind` в каждой строке, чтобы можно
  было различить напоминания и задачи.

## 3. Компромиссы и открытые ограничения

- **TTS не возвращает синхронную ошибку** (`tts.Dispatcher.Speak`,
  тот же контракт, что и у `speak_reply`) — напоминание, доставляемое
  голосом, всегда получает `StatusSent`, даже если колонка недоступна.
  Это существующее ограничение TTS-стека, не то, что чинит этот документ.
- **Резидуальный риск для `create_scheduled_task`.** Разделение убирает
  цикл для подавляющего большинства случаев (простые «напомни»), но если
  модель всё же напишет промпт агентской задачи в рефлексивной форме,
  тот же класс проблемы теоретически возможен и там — просто гораздо реже,
  так как агентская задача по своей природе описывает действие, а не
  напоминание самой себе.
- **`resolveConversation` остаётся привязан только к `userID`** — это
  осознанная архитектура сессий (см. `../../CLAUDE.md`, "Session
  ownership"), которую этот документ не трогает; для напоминаний проблема
  снимается тем, что `Handle` для них вообще не вызывается.

## 4. Проверка после реализации

1. «Напомни мне через 10 секунд полить кактус» → через 10 секунд приходит
   уведомление в исходный канал (+ Telegram), `list_scheduled_tasks`
   после этого пуст (одноразовая задача удалена), в `logs/llm.log` **нет**
   нового хода `Handle` на момент срабатывания.
2. То же самое, созданное через Telegram, с `announce_aloud: true` —
   приходит и в Telegram, и озвучивается (если TTS-устройство доступно).
3. Напоминание, созданное в вебе (без Telegram-чата у пользователя) —
   всё равно появляется в истории диалога веб-UI.
4. Существующие до миграции строки `scheduled_tasks` (из прод-БД до этого
   изменения) после апгрейда продолжают срабатывать как обычные плановые
   задачи через `Handle`, без каких-либо изменений в поведении.
